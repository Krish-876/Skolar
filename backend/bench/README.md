# bench/ -- measurement harness

This is a small harness for deciding provider-hierarchy questions (reasoning
effort, model tier, `k`, `alpha`) **with numbers instead of guesses**, by
running Skolar's actual retrieval/reranking code against labelled
classification data.

**This is NOT a replication of the Diverse-ICL (SIGIR'25) paper.** We reuse
its four datasets and its retrieve-then-rerank *method* (top-k retrieval,
optionally MMR-reranked from a larger pool), but not its models or
hyperparameters. Results here are **not comparable** to the numbers in that
paper's table -- different models (Groq-hosted, not LLaMA3.1-8B/Mistral-7B/
Phi3-2.8B), different `k`/`alpha`/pool sizes, different prompts.

Every retrieval and reranking call in this harness goes through
`backend/pyq/rag/core/{retrieval,mmr,features}.py` -- `retrieve_top_k`,
`mmr`, `SbertBackend`, `TfidfBackend` are imported, never reimplemented. The
point of this harness is that its numbers describe the code Skolar actually
ships, not a separate research implementation.

## Layout

| File | Purpose |
|---|---|
| `datasets.py` | Loads the vendored JSONL, extracts text/labels per dataset. |
| `select.py` | The three ICL settings (`zero_shot`/`few_shot`/`mmr_few_shot`), built on `core.retrieval.retrieve_top_k` and `core.mmr.mmr`. |
| `prompts.py` | One prompt builder per dataset, so every setting shares identical wording -- only the examples differ. |
| `run.py` | CLI that runs a single configuration end-to-end against Groq and writes results. |
| `cache.py` | On-disk response cache keyed on `(model, reasoning_effort, prompt)` -- what makes re-running a sweep cheap. See [Sweeping](#sweeping). |
| `sweep.py` | Runs a grid of `run.py` configs from a YAML spec, with a `--estimate` cost preview and a hard `max_calls` budget. See [Sweeping](#sweeping). |
| `sweeps/default.yaml`, `sweeps/full.yaml` | The cheap default grid and the wider opt-in grid `sweep.py` reads. See [Sweeping](#sweeping). |
| `score.py` | Reads one or more results files and prints accuracy / macro-F1 / parse-failure rate / token totals. |
| `report.py` | Turns one sweep of `run.py` outputs into `results/REPORT.md` + an appended row in `results/history.jsonl`. See [Reporting](#reporting). |
| `subsample_data.py` | The script that produced `data/*/train.jsonl` -- stratified subsampling to a row cap. Reproducible/auditable; see below. |
| `data/` | Vendored datasets (see below). |
| `results/raw/` | Raw per-config `run.py` output (`.jsonl` + `.meta.json`). Gitignored, regenerated by running configs. |
| `results/REPORT.md`, `results/history.jsonl` | `report.py`'s output. Committed -- see [Reporting](#reporting). |
| `.cache/<dataset>__<backend[-model]>__<split>.{npy,npz}` | Embedding cache, keyed by `(dataset, backend, split)` -- sbert additionally keys on the embedding model id (`EMBED_MODEL` in `pyq/rag/core/features.py`) so a model change can't silently reuse stale vectors. Deliberately **not** keyed on `--limit`: a run always encodes the full split and applies `--limit` afterward by slicing, so one cache file serves every limit value (see [Determinism](#determinism)). Gitignored, regenerated on first use. |
| `.cache/responses/<sha256>.json` | Groq response cache keyed by `(model, reasoning_effort, prompt)` -- see [Sweeping](#sweeping). Gitignored, regenerated on first use. |

## Datasets

`data/{SST2,COLA,RTE,TREC}/{train,val,test}.jsonl` are vendored copies of the
four Diverse-ICL datasets, taken from
[github.com/Krish-876/Diverse-ICL](https://github.com/Krish-876/Diverse-ICL)
at commit
[`0d4d7d74580fc5de05f6a8310af83034274b8c6a`](https://github.com/Krish-876/Diverse-ICL/tree/0d4d7d74580fc5de05f6a8310af83034274b8c6a)
(`Datasets/{SST2,RTE,TREC,COLA}/*.jsonl`), which packages GLUE SST2/CoLA/RTE
and TREC-6 for that paper's pipeline. Only the datasets are vendored -- none
of that repo's scripts.

`val.jsonl`/`test.jsonl` are vendored as-is, byte-for-byte. `train.jsonl` is
**subsampled** by `bench/subsample_data.py` -- see below.

If the `data/` files are ever missing (e.g. a shallow checkout that excluded
them), re-fetch and re-subsample with:

```bash

cp /tmp/diverse-icl/Datasets/RTE/rte_train.jsonl   backend/bench/data/RTE/train.jsonl
cp /tmp/diverse-icl/Datasets/RTE/rte_val.jsonl     backend/bench/data/RTE/val.jsonl
cp /tmp/diverse-icl/Datasets/RTE/rte_test.jsonl    backend/bench/data/RTE/test.jsonl
cp /tmp/diverse-icl/Datasets/TREC/trec_train.jsonl backend/bench/data/TREC/train.jsonl
cp /tmp/diverse-icl/Datasets/TREC/trec_val.jsonl   backend/bench/data/TREC/val.jsonl
cp /tmp/diverse-icl/Datasets/TREC/trec_test.jsonl  backend/bench/data/TREC/test.jsonl
```

### train.jsonl subsampling

The retrieval corpus a bench run draws its candidate pool from only needs
enough examples to draw a pool of ~50 from (`select.py`'s
`pool_multiplier * k`) -- it doesn't need the full training split, and a
smaller vendored corpus keeps this repo lighter. `bench/subsample_data.py`
subsamples each dataset's `train.jsonl` to **at most 5000 rows**, stratified
by label so the class distribution is preserved (largest-remainder
rounding), using `numpy.random.RandomState(seed=0)`. A dataset already at or
under the cap is kept whole, unchanged.

| Dataset | Rows before | Rows after | Subsampled? |
|---|---:|---:|---|
| SST2 | 63982 | 5000 | yes |
| COLA | 7696 | 5000 | yes |
| RTE | 2241 | 2241 | no (already under the 5000 cap) |
| TREC | 4907 | 4907 | no (already under the 5000 cap) |

- **Source:** [github.com/Krish-876/Diverse-ICL](https://github.com/Krish-876/Diverse-ICL) @ `0d4d7d74580fc5de05f6a8310af83034274b8c6a`
- **Seed:** `0` (`numpy.random.RandomState(0)`)
- **Cap:** 5000 rows

Because the retrieval corpus for SST2 and COLA is a stratified 5000-row
*subset* of their full training splits rather than the full split, **results
from this harness are not comparable to any run over the full training
corpus** (this harness's own full-corpus results included, if it's ever run
against the un-subsampled vendored files) -- a smaller, differently-composed
candidate pool changes what `retrieve_top_k`/`mmr` can select from.

Per-dataset text/label handling (see `datasets.py`):

| Dataset | Text field(s) | Label map |
|---|---|---|
| SST2 | `sentence` | `{0: negative, 1: positive}` (fixed) |
| COLA | `sentence` | `{0: unacceptable, 1: acceptable}` (fixed) |
| RTE | `sentence1` + `sentence2` | `{0: entailment, 1: not entailment}` (fixed) |
| TREC | `text` | derived from the data itself (the set of distinct `label` strings actually present) -- not hardcoded, so a change to the vendored file is reflected automatically |

## Sweeping

The fastest way to see this harness do something is:

```bash
cd backend
python -m bench.sweep --estimate
```

That's deliberate -- run it before anything else in this file. It costs
nothing (pure CPU work, no API calls) and tells you exactly what a real sweep
would spend before you spend it. Everything below this section (`run.py`,
`score.py`, `report.py`) is the lower-level machinery `sweep.py` builds on;
reach for those directly only when you want one specific config, not a grid.

Running many `run.py` configs by hand (see [Running](#running) below) is fine
for one-off configs, but a real grid (multiple datasets/settings/k/alpha/
seeds) needs cost controls or it's easy to blow through Groq's free tier
without noticing. `bench/sweep.py` expands a YAML grid into `run.py` configs
and runs them in-process (never a subprocess per config), so
`pyq.rag.core.features`'s process-wide `SentenceTransformer` singleton loads
once for the whole sweep instead of once per config.

The `--estimate` command above builds every prompt every config in the grid
would send (pure CPU work -- retrieval/MMR selection and prompt formatting,
no API calls) and checks each one against the on-disk response cache,
printing:

```
configs:          8
total rows:       400  (= calls with an empty cache)
cache hits:       209
net new calls:    191
est. tokens:      ~27,667 (prompt + completion, net-new calls only, rough)
max_calls budget: 300

within max_calls budget.
```

`net new calls` is the number that matters -- it's what this invocation would
actually spend *right now*, given what's already cached, not a worst-case
count that assumes an empty cache.

Then run it for real with the same flags minus `--estimate`:

```bash
python -m bench.sweep
python -m bench.sweep --config bench/sweeps/full.yaml
```

### Response cache

`bench/cache.py` caches each Groq response on disk under
`.cache/responses/<sha256>.json`, keyed by `sha256(model + reasoning_effort +
the exact prompt string)`. On a hit, `run.py` skips the API call entirely and
marks the row `"cached": true` (see [Output](#output)). This is the reason a
sweep is cheap to re-run: a zero_shot prompt doesn't depend on k/alpha/seed
at all, and retrieval/MMR selection is currently fully deterministic (see
[Determinism](#determinism)), so two configs that differ only in an axis that
doesn't change the prompt -- or a config re-run against unchanged data --
produce byte-identical prompts and collapse to one real call.

### `--estimate` and `max_calls`

Every sweep grid YAML must set a `max_calls` key. If the expanded grid's
*net-new* call count (after subtracting cache hits) exceeds it, `sweep.py`
refuses to start and prints the estimate instead -- a sweep can never
silently spend more than the budget you set. There's no silent fallback
default: a grid YAML missing `max_calls` fails to load at all, on purpose.

### Grid YAML schema

```yaml
max_calls: 300              # required -- hard budget on net-new calls
model: openai/gpt-oss-120b   # required
reasoning_effort: none      # optional, default "none"
backend: sbert               # optional, default "sbert"
pool_multiplier: 3           # optional, default 3
limit: 50                    # optional, default null (full test split)
out_dir: bench/results/raw   # optional, default "bench/results/raw"

datasets: [sst2]                              # optional, default all four
settings: [zero_shot, few_shot, mmr_few_shot] # optional, default all three
k: [4]                       # optional, default [4]
alpha: [0.3, 0.7]            # optional, default [0.7]
seeds: [0, 1]                # optional, default [0]
```

`k`/`alpha`/`seeds` are expanded per-setting, not as one flat cross product:
`zero_shot` ignores both `k` and `alpha` (only `seeds` varies it), `few_shot`
ignores `alpha`, and `mmr_few_shot` uses both. Looping an axis a setting
doesn't read would just enumerate literal duplicate configs -- the response
cache would make the repeats free API-cost-wise, but there's no reason to
even generate them.

Two grids ship in `bench/sweeps/`:

- **`default.yaml`** -- what `python -m bench.sweep` runs with no `--config`.
  One dataset (sst2), `--limit 50`, `k=[4]`, `alpha=[0.3, 0.7]`,
  `seeds=[0, 1]`, `max_calls: 300`. Cheap enough to re-run casually.
- **`full.yaml`** -- every dataset, the full test split, a much wider
  k/alpha/seed grid, `max_calls: 5000`. Opt-in via `--config
  bench/sweeps/full.yaml`; always `--estimate` it first and raise
  `max_calls` to whatever that actually prints, not blindly.

## Running

```bash
cd backend
python bench/run.py \
    --dataset sst2 --setting mmr_few_shot \
    --k 4 --alpha 0.7 --pool-multiplier 3 \
    --backend sbert --model openai/gpt-oss-120b --reasoning-effort none \
    --limit 5 \
    --out bench/results/raw/sst2_mmr_smoke.jsonl
```

`--out` is unaffected by `report.py`'s existence -- pass it whatever path you like.
Point it at `bench/results/raw/` so `report.py`'s default `--results-dir` finds it
without extra flags (see [Reporting](#reporting)).

Requires `GROQ_API_KEY` in the environment (same as the rest of `pyq.rag`;
`run.py` reuses `pyq.rag.llm.client.get_groq_client`).

### Flags

| Flag | Meaning |
|---|---|
| `--dataset` | One of `sst2`, `cola`, `rte`, `trec`. |
| `--setting` | `zero_shot` (no examples), `few_shot` (top-`k` by `retrieve_top_k`), `mmr_few_shot` (retrieve a pool of `pool_multiplier * k`, then `mmr` reranks it to `k`). |
| `--k` | Number of in-context examples (ignored for `zero_shot`). |
| `--alpha` | MMR relevance/diversity tradeoff (`mmr_few_shot` only). |
| `--pool-multiplier` | Pool size for `mmr_few_shot` is `pool_multiplier * k`, capped at the train corpus size. |
| `--backend` | `sbert` (`all-MiniLM-L6-v2`) or `tfidf`. Both are `pyq.rag.core.features` backends. |
| `--model` | Groq model id. **Always required** -- `run.py` never falls back to `llm/client.py`'s hardcoded `GROQ_MODEL`, so different models can be compared directly. |
| `--reasoning-effort` | `none`, `low`, `medium`, or `high`. Passed as Groq's `reasoning_effort` param. `none` **omits the param entirely** rather than sending the literal string, since this is a separate axis from `--model` -- you can hold the model fixed and sweep this. |
| `--limit` | Only run the first N test samples (sorted by id). Omit for the full test split. |
| `--seed` | Random seed, default `0`. Currently only guards library RNG state -- retrieval/MMR selection is fully deterministic (see [Determinism](#determinism)), so this has no effect on output today. Plumbed through end to end (including into `bench/sweep.py`'s grid) so it's ready the day selection gains any seed-dependent behaviour. |
| `--out` | Output JSONL path. A `<out>.meta.json` sidecar recording every CLI arg is always written alongside it. |

### Output

One JSONL row per sample: `id`, `gold`, `raw_completion`, `prediction`
(`null` on parse failure -- never silently dropped), `prompt_tokens`,
`completion_tokens`, `cached` (`true` if this row was served from the
response cache instead of a live API call -- see [Sweeping](#sweeping)).

`<out>.meta.json` records every CLI arg plus `seed`, `n_samples_total`,
`n_samples_written`, `n_cache_hits` (how many of those rows were served from
the response cache -- see [Sweeping](#sweeping)), `started_at`/`finished_at`,
and `partial` (`true` if the run stopped before finishing all samples -- e.g.
the Groq daily cap was hit -- so a results file is always traceable to
exactly the config and coverage that produced it).

### Determinism

- `temperature=0`, a fixed internal seed, and sorted iteration (test samples
  are always processed in ascending id order) -- two runs with identical args
  against identical model responses produce byte-identical output files.
- Encodings are cached to disk under `.cache/`, keyed by
  `(dataset, backend, split)` (plus the embedding model id for sbert), so
  re-running the same dataset/backend combo doesn't re-embed. The cache is
  always built from the **full** split -- `--limit` is applied afterward by
  slicing the already-encoded result -- so one cache file is valid for every
  `--limit` value, including no limit at all. As a safety net, a cached
  array whose row count doesn't match the current (full) split is treated as
  a miss and re-encoded, so a cache file written by a version of `run.py`
  that didn't have this guarantee self-corrects on next use instead of
  silently mismatching against the sample count.
- This guarantees *our* harness is deterministic. It does not guarantee the
  Groq API itself returns identical completions run-over-run -- that's
  outside this harness's control (though the response cache means a
  re-run against the same prompt reuses the *first* run's completion rather
  than asking Groq again -- see [Sweeping](#sweeping)).

### Rate limits

Groq's free tier is 30 requests/minute and 1000 requests/day. `run.py`:

- proactively throttles to 30 RPM client-side (not just reactive backoff),
- retries on 429 with backoff,
- detects a daily-cap 429 (or exhausting the RPM retry budget) and stops the
  run immediately rather than burning through remaining retries -- the
  partial output and `.meta.json` (`partial: true`) are still written, so
  nothing already spent is lost, and the failure is loud (a raised
  `SystemExit` with the partial-file path), never a silent truncated file.

## Scoring

```bash
python bench/score.py bench/results/raw/a.jsonl bench/results/raw/b.jsonl
```

Prints a comparison table: `n`, `accuracy`, `macro_f1`, `parse_fail_rate`,
`prompt_tok`, `completion_tok`, one row per file. Parse failures count
against accuracy and macro-F1 like any other wrong answer (never dropped
from the denominator), and are also reported as their own rate so a bad
prompt can be told apart from a bad model.

## Reporting

`report.py` turns one sweep of `run.py` outputs into a single persistent
`bench/results/REPORT.md`, plus one appended row in `bench/results/history.jsonl`.
It only reads what `run.py`/`select.py` already wrote/computed -- it never
reimplements or re-tunes anything in `pyq.rag.core`.

Copy-pasteable smoke sequence (zero_shot baseline + few_shot + mmr_few_shot on
one dataset, capped at 20 samples so it's fast and cheap) followed by the
report invocation:

```bash
cd backend

# Smoke sequence: zero_shot baseline + few_shot + mmr_few_shot on COLA, capped
# at 20 samples so it's fast and cheap to sanity-check end to end.
python bench/run.py --dataset cola --setting zero_shot \
    --model openai/gpt-oss-120b --reasoning-effort none \
    --limit 20 --out bench/results/raw/cola_zero_shot.jsonl

python bench/run.py --dataset cola --setting few_shot --k 4 \
    --backend sbert --model openai/gpt-oss-120b --reasoning-effort none \
    --limit 20 --out bench/results/raw/cola_few_shot_k4.jsonl

python bench/run.py --dataset cola --setting mmr_few_shot --k 4 --alpha 0.7 \
    --backend sbert --model openai/gpt-oss-120b --reasoning-effort none \
    --limit 20 --out bench/results/raw/cola_mmr_k4_a0.7.jsonl

# Turn every raw config under bench/results/raw/ into bench/results/REPORT.md,
# and append one row to bench/results/history.jsonl.
python bench/report.py --results-dir bench/results/raw --out-dir bench/results
```

(This block is kept verbatim identical to the "How to run" section `report.py`
writes into `REPORT.md` itself -- update both together if either changes.)

`--results-dir` defaults to `bench/results/raw` and `--out-dir` defaults to
`bench/results`, so plain `python bench/report.py` with no flags works once
raw output lives under `results/raw/`.

### REPORT.md structure

`REPORT.md` has two halves, split by `<!-- BENCH:BEGIN -->` / `<!-- BENCH:END -->`
marker comments:

- **Above the markers**: static and hand-editable -- this "How to run" section
  and the full metric glossary (what each health/diversity metric means, which
  direction is good, which knob to turn). Written once, when `REPORT.md` doesn't
  exist yet, and **never rewritten** by `report.py` after that.
- **Between the markers**: regenerated on every `report.py` run -- run header,
  health status, results, diversity, and verdict for whatever sweep is
  currently under `--results-dir`.

If `REPORT.md` exists but is missing a marker (or has them duplicated or out of
order), `report.py` refuses to guess and exits with an error instead of
overwriting hand-edited content -- restore the markers by hand, or delete the
file to have it regenerated fresh.

### history.jsonl

Append-only, one JSON object per `report.py` run: `timestamp`, `git_sha`
(+ `git_dirty`), `models`, `config_grid`, a compact `health` summary
(`partial`, `configs_total`, `configs_completed`, `api_errors`,
`degenerate_sets`), and `configs` (per-config `accuracy`/`macro_f1`/
`delta_vs_zero_shot` plus diversity metrics). Existing lines are never
rewritten. Fields the harness genuinely can't supply yet (`api_errors`) are
`null`, never `0` and never a guess -- see the metric glossary in `REPORT.md`
for what's not recorded and why.

## Tests

`backend/tests/test_bench_*.py` cover `datasets.py` parsing, `select.py`
setting behaviour, `prompts.py` formatting, `score.py` metrics on synthetic
data, `run.py`'s own rate-limit/partial-meta and CLI-plumbing logic, the
response cache (`cache.py`), and `sweep.py`'s grid expansion/`--estimate`/
`max_calls` logic -- all against a faked Groq client (or no client at all for
the cache/estimate paths), no real API calls or quota spent. Run them with:

```bash
cd backend
python -m pytest tests/test_bench_datasets.py tests/test_bench_select.py \
    tests/test_bench_prompts.py tests/test_bench_score.py tests/test_bench_run.py \
    tests/test_bench_cache.py tests/test_bench_sweep.py
```
